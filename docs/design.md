# mac-server-kit design

Decisions settled before implementation. Each section gives the decision first, with any reasoning that affects later choices.

## Scope

- Audience: the owner, his brother, and a few friends. Prompts, an answers file and a README checklist are enough. No hardening for strangers' machines.
- Private repo for now and possibly public later. Because publishing exposes the full history, nothing machine-specific is ever committed.
- Complete break from the original `mac-media-stack` project. The only connection is a credit in the README.
- Platform: macOS only, with Docker via OrbStack. Intel and Apple Silicon. Some target Macs have no Homebrew.

## Language

Bash 3.2 (stock macOS), no dependencies. Chosen over zsh for readability; the installer behaves the same for users either way. The module design avoids needing associative arrays by discovering module folders and reading small key=value files.

## Commands (hybrid)

From the repo checkout:

```
./kit prepare [--vpn <provider>] [--media-server <choice>] [<module>...]
                                   # what to have ready before installing
./kit prepare ... --answers-template <file> --secrets-template <file>
./kit install                      # prompts, or: ./kit install [--answers <file>] [--secrets <file>]
./kit install --plan [...]         # what an install would change, changing nothing (also add|disable --plan)
./kit check                        # can this Mac run it, and is it ready? (changes nothing)
./kit add <module>
./kit disable <module>
./kit status                       # enabled modules, holds and their age, to-dos, health summary
```

`prepare` reads everything from the modules, so it can't drift from what `install` asks for. It uses this machine's answers when there are any, the defaults otherwise, and the flags and named modules on top. It's read-only apart from the templates it writes. Each asked key has a line in its module's `help` file: one sentence on what the service is and what the kit uses it for, then where to get it, naming the provider's actual page and setting (e.g. ProtonVPN → Downloads → WireGuard configuration, NAT-PMP on). The same text shows above the install prompt and in the templates. Items that aren't keys (accounts, tailnet settings, admin password, being at the screen for OrbStack) live in a per-module `ready` file. The list is grouped into: needed during the questions (`before`), about the machine (`machine`), and after the first start: to-dos (`after`) and notes (`note`), so nobody stalls looking for them. An install lists the to-dos under Still to do, and the notes under Good to know only for the modules it added (all of them on a first install). Where the kit can check a to-do, its line carries `!done:<name>` and the install records what it saw on every run (`todo_mark`, files in `~/server/kit/done/`), so a done step leaves the list and an undone one comes back: automatic login (`defaults read` of loginwindow's `autoLoginUser`), Prowlarr's indexers, Seerr's setup, Homarr's setup page (`onboard.currentStep` at `finish`), Plex's sign-in and both libraries, RomM's games (`/api/stats`), and Tracearr's steps (`!TRACEARR_API_KEY?`). What it can't check, and what's only information (the admin accounts it made, how updates work), are notes. `./kit status` shows the to-dos too.

The secrets template is a fill-in `secrets.conf` holding only the keys the user supplies for the given VPN provider and modules, each with its hint. Required keys are present and empty. Optional keys are commented out, so install still asks about them unless the user uncomments one and leaves it empty to skip it for good. Typical use: the owner fills in keys for another person's machine, sends the file privately, and they run `./kit install --secrets <file>`.

The answers template is the same for `answers.conf`: every asked answer with its default (or this run's choice) filled in, `~/` paths that mean the target Mac's home folder, the `MODULES=` line, and the never-asked settings commented out. With both templates filled in, install asks nothing, once each optional key in the secrets template is uncommented (left empty to skip it). Optional keys left commented out are asked, with Enter to skip. That also makes test runs repeatable. `--answers` and `--secrets` copy the file into place only when there's no file there yet, and only once the questions are done and every value has passed its check: until then the run works on a draft in `~/server/kit/`, so an install that's quit, or stopped by a bad value, leaves nothing behind and can be rerun with the corrected file. Messages about a value name the user's own file. Without these options, answers typed at the prompts are saved as they're given, so an interrupted run keeps them. A required key left empty is asked again (its new line is appended, since the last line wins).

Installed to `~/server/bin` for runtime, used by launchd and by hand:

```
update-all            update-<module>
backup-all            backup-<module>       backup-config
restore-<module> [backup]                   restore-config
check-health          show-health-history
start-maintenance     end-maintenance
copy-backups
```

`backup-<module>`, `restore-<module>` and `update-<module>` are one-line wrappers around the generic `backup-project`, `restore-project` and `update-project <project>`. The scripts share `kit-runtime.sh` (paths, `runtime.conf`, logging, maintenance windows, image pins) and `kit-registry.sh` (release-tag lookups, which `./kit install` sources from the repo too), both sourced, not run.

## Layout on a machine

- `~/server/<project>/`: compose projects (media stack, separate-project modules)
- `~/server/appdata/<project>/`: app data
- `~/server/backups/<project>/<project>-<date>/`: local backups (keep 8), and `~/server/backups/config/config-<date>/`
- `~/server/bin/`: runtime scripts. Install puts it on the PATH by adding one marked line to `~/.zprofile` (created if missing), only if that line isn't there yet. This is the one write to a file outside `~/server` that the user owns.
- `~/Library/LaunchAgents/io.github.andy327.mac-server-kit.<job>.plist`: the kit's launchd jobs, generated each install from the modules' `jobs` files (launchd loads a user's jobs at login only from there). A job no enabled module declares is unloaded and its plist removed. Job output goes to `~/server/logs/<job>.log`.
- `~/server/logs/`: health logs
- `~/server/local-modules/`: git-ignored, machine-only modules (same layout as repo modules)
- `MEDIA_ROOT` (default `~/Media`: Downloads/complete, Downloads/incomplete, Movies, TV Shows) and `GAMES_ROOT` (default `~/Games`). Asked once and stored in the answers file, so they can move to an external drive later. Either may be a real folder or a symlink (`~/Media` pointing at `/Volumes/<drive>/Media`, the layout `docs/external-drive.md` recommends when moving an install onto a drive, since native Plex and Jellyfin keep their paths). The kit never replaces a symlink and never makes anything under `/Volumes` unless a drive is mounted there (`mount` lists it); a link to nowhere or an unmounted drive stops the install with what to fix. Containers mount the real folder: `.env` gets `MEDIA_REAL` and `GAMES_REAL` (`${KIT_REAL_<answer>}` in an env file: the answer with symlinks followed). Native apps keep the answer's own path.
- One mount for media: qBittorrent, Sonarr, Radarr and Bazarr mount `MEDIA_REAL` once, at `/data`, so imports are hardlinks (separate bind mounts of the same disk can't hardlink and every import is a copy). The mounts use compose's long form with `create_host_path: false`, as does RomM's library: when the drive isn't mounted, a container fails to start instead of Docker making an empty folder where the drive goes. Paths inside: `/data/Downloads/complete` and `incomplete`, `/data/Movies`, `/data/TV Shows`.
- External drives at runtime: `runtime.conf` lists the drives each project keeps files on (`VOLUMES_<project>`), all of them with their folders (`MEDIA_VOLUMES`), and the folders on the Mac's own disk (`LOCAL_MEDIA`). update-project and restore-project refuse when a drive isn't mounted. After a restart OrbStack starts containers before macOS may have mounted the drive, and those fail to start (above), so the `wait-volumes` job (schedule `login`: once at login) waits up to 30 minutes for the drives, then for Docker, and runs `docker compose up -d` for those projects; with no drives it exits at once. It logs what `docker info` said when Docker doesn't answer. check-health names the containers stopped because their drive is missing (from their mount sources) in one diagnosis, with no per-container start advice and no diagnosis for their nodes' 502s. `./kit install` stops at a MEDIA_ROOT or GAMES_ROOT on a drive that isn't mounted.
- `.env` files use absolute paths, not `~`.
- `APPS_DIR` (Advanced answer, default `/Applications`): where the kit installs native apps (Plex, Jellyfin, Ollama). Set it to `~/Applications` to keep the apps in one user's account, as on a test account. Brew casks get `--appdir "$APPS_DIR"`. The kit looks for an app in `APPS_DIR` and then `/Applications`, so one already installed isn't installed again, and launchd jobs point at wherever the app is. Apps the kit doesn't install (OrbStack, the host's Tailscale) stay wherever the user put them.

## Base install

- Gluetun: ProtonVPN default (port forwarding wired up), NordVPN as an option (WireGuard/NordLynx, no port forwarding). No other providers, and no extra DNS or HTTP-proxy settings.
- qBittorrent, Prowlarr, Sonarr, Radarr, Bazarr (subtitles; mounts Movies and TV Shows), FlareSolverr (Prowlarr's indexer proxy), Seerr
- Media server: the installer asks Plex, Jellyfin, or both. Seerr and Tracearr follow the choice.
- Native apps (`lib/native.sh`, each module's `hooks/install`, run in its own "Native apps" step before the projects start): an app already in `APPS_DIR`, `/Applications` or `~/Applications` isn't installed again. Otherwise the install uses Homebrew when it's there, and the vendor's own download when there's no Homebrew or it fails (as when it belongs to another account), checked against the vendor's published checksum. A failed install warns and the rest goes on. Each app runs from a kit launchd job with the `always` schedule (`RunAtLoad`, and `KeepAlive` unless it exits normally), whose runner script (`run-plex`, `run-glances`) finds the app and runs it in the foreground. If the app is already running, started some other way, the runner watches that copy instead of starting a second. `run-plex` and `run-jellyfin` set `RUN_AFTER_DRIVES=media-stack`, so `run_app` first waits, with no time limit, for the drives in `VOLUMES_media_stack`: an app started before macOS mounts the drive would see empty library folders, and a scan then could drop what's missing. The runner logs one "Waiting for <drive> to be mounted" line (again every 10 minutes), and check-health, finding that line at the end of the job's log, says the app is waiting for its drive instead of suggesting a kickstart. check-health's native app lines (`NATIVE_HEALTH`) name the job as `job:<name>`, so its advice is `launchctl kickstart -k` of that job. `disable` (or a media server change) unloads the job, which stops the app; the app and its data stay.
- Plex: the `plex-media-server` cask, or the universal zip from plex.tv's download list (`plex.tv/api/downloads/5.json`, with its SHA-1). `plex-proxy` (socat, in the media stack) relays it to the compose network as `plex-proxy:32400`, because Homarr rejects `host.docker.internal`'s address. Once someone has signed in to Plex (its token appears in the `com.plexapp.plexmediaserver` preferences), the install adds Sonarr's and Radarr's "Plex Media Server" connection, with `/tv` and `/movies` mapped to the folders on this Mac for its rescans (each waits until Plex has a library of its kind: Sonarr and Radarr refuse the connection before that), and a Homarr tile and widget connection. Seerr's own setup is pointed at `plex-proxy`. Plex updates itself; update-all leaves it alone.
- Jellyfin: the `jellyfin` cask, or the .dmg that Homebrew's public cask data points at (`formulae.brew.sh/api/cask/jellyfin.json`, read with curl so Homebrew needn't be installed: the version, and a url with its SHA-256 for each processor), mounted with `hdiutil` and copied with `ditto` (`modules/core/bin/kit-dmg.sh`, shared by the install and update-jellyfin). jellyfin.org publishes no checksum files of its own. Jellyfin.app is a small menu bar launcher that runs `Contents/MacOS/jellyfin --webdir Contents/Resources/jellyfin-web --ffmpeg Contents/MacOS/ffmpeg --datadir <data>`, the data in `~/.local/share/jellyfin` if that exists, else `~/Library/Application Support/jellyfin`; `run-jellyfin` runs that server the same way, so there's no menu bar icon. `jellyfin-proxy` relays it to the compose network. The kit sets Jellyfin up itself, as it does Homarr, right after its job starts (so nobody else on the network claims a fresh one): the first-run steps (`/Startup/...`, open until they're completed) with the admin account (`admin`, the generated `JELLYFIN_ADMIN_PASSWORD`) in this Mac's language and region, then an API key for the kit made by signing in as admin (`generated-secrets.conf`), Movies and TV Shows libraries on the media folders, Sonarr's and Radarr's "Emby / Jellyfin" connection (`MediaBrowser`, paths mapped as for Plex) and a Homarr tile and widget connection. A Jellyfin set up by hand needs a key from its owner, `JELLYFIN_API_KEY` in `secrets.conf`. Its own Tailscale node (`jellyfin`, default name `jellyfin`) is public with `EXPOSE_jellyfin=funnel` once its `config/system.xml` says the setup is done; the install writes the serve files again after the wiring, so that happens in the same run. Jellyfin doesn't update itself: `update-jellyfin` (in update-all) runs `brew upgrade --cask` for a Homebrew install, or swaps in the newer .dmg, stopping and starting its job.
- The stack's Tailscale node, logged in with auth keys (not printed login URLs, to avoid a login race)
- Homarr on its own Tailscale node (default name `dashboard`)
- Tailscale details: each node is a `tailscale/tailscale` container (`<node>-tailscale`) in its project, logged in once with `TS_AUTHKEY` (`TS_AUTH_ONCE`), its state in app data, healthy once it has its tailnet address. The auth key carries a tag (`tag:server`), so the nodes' logins never expire; that needs a `tagOwners` entry in the tailnet policy first, and Funnel's policy entry has to list the tag too (tagged machines aren't `autogroup:member`). What a node serves comes from the modules' `serve` files (`node|port|path|target|when|funnel`); the kit generates `~/server/<project>/tailscale/<node>/serve.json` from them, mounted as a folder so a change applies without a restart. Funnel is port 443 only, needs `EXPOSE_<node>=funnel`, and waits until the app behind it is set up (Seerr: until someone has signed in), so no stranger can claim a fresh app first. After the start the kit reads each node's real address (Tailscale adds `-1` when a name is taken) into `~/server/kit/tailnet.conf`, warns about a taken name, a missing tag, MagicDNS or HTTPS certificates being off, and shows the tailnet addresses in the report
- Glances, native, 10-second refresh (lower CPU than the 2s default), process lists off. Installed with brew if present, else (or if brew fails) with uv (`uv tool install 'glances[web]'`, uv itself from its standalone installer into `~/.local/bin`, with `UV_NO_MODIFY_PATH` so it leaves shell profiles alone). `update-glances` (run by update-all) upgrades it the same way and restarts its job when the version changed. uv is the no-Homebrew path for every Python tool the kit installs; never `pip --user`. Glances binds `127.0.0.1` (not `0.0.0.0`): under OrbStack, `host.docker.internal` reaches services that listen only on the Mac's loopback, so glances-proxy still works and Glances stays off the LAN. Its config is generated into `~/server/kit/glances.conf` and passed with `-C` (Glances doesn't find one in macOS's settings folders): `[fs] show=` lists the disks it reports, `GLANCES_DISKS` (an unasked answer) or only this Mac's data volume (`/System/Volumes/Data`, not `/`); a change restarts its job. Drives aren't added by default: the widget has room for one disk ring beside CPU and memory, and check-health already watches each media and games drive's free space. The Mac Host Info widget shows each disk Glances reports (the data volume and drives under `/Volumes`), in TB from 1 TB, labelled SSD or by the drive's name when there's more than one. The install warns when another launchd job runs Glances (an older setup's), since the kit's job then only watches it.
- Health (the `health` module, ported from the reference's scripts): check-health (a report with a diagnosis, or `--log`: one sample every 5 minutes from the `log-health` launchd job, incident snapshots, a Healthchecks.io check-in, ntfy alerts), show-health-history, export-health-status, start/end-maintenance, and the media stack's check-media-stack. What they check comes from the generated `~/server/kit/runtime.conf` (mode 600): the projects, the Healthchecks URL and optional API key, the ntfy URL, `HOST_TAILSCALE`, and native apps from the modules' `NATIVE_HEALTH` lines (`name|port|path|fail or warn|how to start|extra logs`, several separated by `;`). ntfy alerts go out when something breaks, when it recovers, and when the Mac is back after a restart or a gap; not inside a maintenance window or while an update-, backup- or restore- script runs. The install checks in with Healthchecks.io once and sends an ntfy test message the first time a topic is set. health-web (nginx, a service in the media stack, its config inline in its compose file) serves `status.json` and the newest incident zip from `~/server/logs/health/web`, to Homarr's "Server health" custom widget as `http://health-web` and on the dashboard node at `/health/` (which the widget's download link uses). Healthchecks.io and ntfy are both optional (secrets prompts). Linking a Healthchecks check to ntfy is a manual checklist step. With port forwarding on (ProtonVPN), check-health also checks that qBittorrent listens on Gluetun's forwarded port (`/tmp/gluetun/forwarded_port`, qBittorrent's API through `docker exec gluetun wget`, which needs no login) and sets it when it doesn't, logging each fix in `~/server/logs/health/fixes.log`: Gluetun's up command retries for only about 3 minutes, and qBittorrent with many torrents can take longer to start. Within 10 minutes of either starting, or of the port changing, a fix is only noted; after that, a mismatch is a failure (`media:port-sync(qBittorrent <old>, Gluetun <new>)`) even once fixed, so it gets a snapshot and an alert, and the next sample recovers. No forwarded port 10 minutes after Gluetun started is a warning. Short network blips aren't outages:
  - A Tailscale node that loses the coordination server but keeps its relay and a live peer link is a warning with no restart advice. It counts as down only when the next sample finds it the same; `--log` keeps the nodes seen that way in `~/server/logs/health/.ts-coord`.
  - A tailnet or Funnel URL that fails gets a second try after 10 seconds. Once a node's URL fails twice, that node's other URLs get one try each.
  - On a server (not a laptop), check-health warns when Wi-Fi and Ethernet are both connected, when traffic goes over Wi-Fi while Ethernet is connected, and when the default gateway isn't `HOME_ROUTER`. That answer is the gateway the first install saw; an empty value turns the check off.
- More of check-health: each drive in `MEDIA_VOLUMES` is mounted (else a failure, `host:media`, with how to mount it) and has space (warn under 10%, fail under 5%, in TB, `host:media-disk`); this Mac's disk hints leave out folders that are on a drive. A hardlink test in qBittorrent's container (a file in `/data/Downloads` linked into `/data/Movies` must have 2 links; one link on an imported file isn't a fault, since a torrent removed after import leaves one) fails as `media:hardlinks`. export-health-status names those three causes. The Mac's own Tailscale app, when disconnected, gets the likely reasons (its network extension needing approval again, an expired key, not opening at login) and `Tailscale up` for its own error. A maintenance window closes by itself only after a restart or a gap, so start-maintenance says to run end-maintenance after work without one, and the full report says so once a window has been open half an hour with everything healthy.
  - Incident snapshots also keep configd's network events (router ARP failures, link changes, network switches) from 10 minutes before the outage, and the current route and network ports.
  - Only this user's runs of this server's own update-, backup- and restore- scripts count as maintenance, so another account's kit on the same Mac doesn't hide an outage.
- Runtime scripts: a module's `bin/` files are copied into `~/server/bin` on each install; `~/server/kit/bin.list` records which are the kit's, so ones no module has any more are removed and the user's own are left alone. They follow `KIT_SERVER_DIR` like the kit, for tests.
- Backups and updates (below)

### Module folder contents

Each module declares:

- compose file, and whether it joins the media stack compose or is its own project
- prompts (with defaults), optionally a `choices` file (`KEY|value|description`: a numbered list under that key's question, the default marked as suggested; a number or any value is accepted), and an `env` file: `KEY|value|when` lines for the project's generated `.env`, where `${NAME}` is an answer, a secret, a generated secret or a kit value (`KIT_PUID`, `KIT_PGID`, `KIT_APPDATA`, `KIT_LOGS`). A line's `when` (also in prompts, serve, ready, help, logins and jobs files) is `KEY=value`, `KEY!=value`, `KEY?` (set), `+module` (enabled), `@mark` (a file the kit writes in the project's app data, such as `kit-admin`; env and serve lines only), `done:name` (a to-do the install last saw done), `!` before any of them for its opposite, or several of them joined with `,`, all of which must hold. A serve line held back by an `@mark` still gives its node a serve.json, with nothing in it, so the node joins the tailnet and serves nothing until the kit has set the app up. A wire hook that writes a mark an env line depends on calls `project_refresh <project>`: the `.env` again, and `up -d` when it changed. A module adds to another project with `env.<project>` and `compose.<project>.yml`
- native prerequisites and how to install them with and without brew
- backup, update and restore scripts
- dependencies on other modules
- Tailscale node name (default, changeable) and exposure (Funnel or tailnet-only default, asked once)
- Homarr apps, and Homarr integrations as a *separate* step (see Homarr)
- a `logins` file, `name|user|key|what|when`: each app's sign-in, for `show-logins`. The install writes the lines into `runtime.conf` with the app's addresses from its `urls` file, the keys' names only; show-logins reads their values from `secrets.conf` and `generated-secrets.conf` when it runs (a test checks that every key is one the kit generates or asks for)
- widgets/integrations it makes available, for the post-install list
- version holds (see Updates)

## Install model

- One idempotent install path. `add` re-runs it with the module enabled. `docker compose up -d` only recreates changed services, so adding a module doesn't restart unrelated ones. A changed `serve.json` applies without restarting its Tailscale node. Install runs: preflight, answers and secrets, folders and the PATH line, generate (`.env`, `compose.d/`, image pins, `serve.json`), seed (`hooks/seed`), then `docker compose up -d --wait --wait-timeout 300 --remove-orphans` per project (`--remove-orphans` takes away a disabled module's containers), reads the Tailscale nodes' addresses, wires the apps (`hooks/wire`, Homarr included) and imports the Homarr custom widgets, installs the runtime scripts, `runtime.conf` and the launchd jobs, and ends with the addresses, the checklist and a short summary: how long it took, what the wiring made (its `✓` lines; the ones that hold on every run use `ok_again` and don't count), which projects restarted with new settings, every warning again, and how many apps and to-dos the lists above hold. Colors and underlined addresses only on a terminal, and never with `NO_COLOR` set or `TERM=dumb`. A project that doesn't start shows `compose ps` and the hints (a module's `hints` file, `service|text`) of the services that aren't running and healthy, and the install stops.
- Each project folder holds a generated `compose.d/` (every enabled module's compose file for it, rebuilt each run, so a disabled module's file is simply gone) and a `COMPOSE_FILE` list in `.env`. The list starts with a generated `project.yml` (just the project name), because Compose resolves `./` in every file against the first file's folder; without it, `./tailscale/...` would point into `compose.d/`. It ends with `compose.override.yml` when the user has one. Plain `docker compose` commands in the folder see the same project. The kit's compose files follow fixed layout rules (two-space services, one `image: repo:tag` line each) so the kit can read their images without a YAML parser; a test enforces the rules.
- File rules: generated files are rebuilt every run; seeded files/settings are create-if-missing; user-owned files are never overwritten or regenerated. The only writes to the answers and secrets files are appending keys that are missing (prompt answers) and editing the single `MODULES=` line (`add`/`disable`). Users customize through `compose.override.yml` per project (Compose merges it automatically) plus the answers and secrets files.
- `.env` files are generated from the answers and secrets files on every run. They are never hand-edited. Each holds `COMPOSE_PROJECT_NAME` and single-quoted values, and is private (600) because it carries keys. A value can't contain a `'` or a line break; the install stops if one would.
- `disable` stops and removes containers (`compose down` without `-v`), unloads launchd jobs, and drops the module from update/backup/health. Volumes and appdata stay. Re-enabling brings it back with data intact. Full removal is not supported.

## Plan (`--plan`)

`./kit install --plan` (with `--answers`/`--secrets` too, and `./kit add|disable <module> --plan`, which set `MODULES=` for that run only) runs the install's steps and prints, under the same section names, what each would change, without changing anything or asking anything (`lib/plan.sh`). It's for adopting a server set up before the kit, and for any install where you want to look first. Lines: `+` the install would do this, `⚠` check before installing, `? can't tell: <why>` (never a guess). A box at the end counts them and repeats the ⚠ lines.

- Lists: answers it would ask for (with their defaults), lines an `--answers`/`--secrets` file adds (secret values never shown), generated secrets it would make (names only), modules it would enable or disable; folders and the `~/.zprofile` line; the power settings it would offer; native apps found or how they'd be installed; each generated file new, changed (a unified diff; any line holding a secret, or whose key looks secret, shows as `KEY=•••`) or unchanged (`.env`, `project.yml`, `compose.d/`, `zz-images.yml`, `serve.json`, `runtime.conf`, `glances.conf`, plists); images it would pull and pin; seeded files it would create or keep; per service create, recreate (why) or remove; runtime scripts and launchd jobs to add, load, reload or remove; and the wiring, read from the running apps.
- Containers: `docker compose config --hash '*'` of the rendered files, run with `--project-directory` the live folder so `./` paths are the real ones, against each container's `com.docker.compose.config-hash` label: the comparison `up` itself makes (checked against Compose 5.6 on a real container).
- Never written: generated files are rendered into a temp folder (`plan_out` maps `~/server/x` under it) and diffed against the live ones; answers, secrets and generated secrets are copies there, as `--answers` drafts are. `KIT_PLAN=1` wraps the command functions: `dk` runs only `ps`, `inspect`, `image inspect`, `info`, `compose config|ps|version`; `kcurl` only GETs and HEADs that write nowhere but the temp folder; `klaunchctl` only `print`/`list`; `kbrew` only `--prefix`; `kpmset` only `-g`; `kdefaults` only `read`; `ksudo` never. `write_generated`, `kv_append`, `kv_replace`, `lock_set` and `plan_guard` refuse any path outside the temp folder; `seed_file`, `make_dir`, `mark_write` and `todo_mark` only list. A refusal stops the step as a kit bug. On top, the kit runs itself again inside macOS's `sandbox-exec`, which denies every file write except the temp folder, `/tmp` (bash 3.2's here-documents go there whatever `TMPDIR` says) and `/dev`; without it the plan says nothing about a sandbox and relies on the rest (`KIT_PLAN_SANDBOX=off` skips it). The first run of the sandbox caught a `mkdir` of `~/Library/LaunchAgents` the guards had missed.
- Hooks: install hooks stop after their "already installed" check with one line. Seed hooks run as they are (`seed_file` lists). Wire hooks run only for projects that have a running container: `api_call` answers any method but GET as if it worked, sending nothing, and the hook's `✓` line becomes a `+` line. Steps that need a POST's answer say what they'd do in one line: Homarr's first account, Jellyfin's setup, key and libraries, the RomM and Karakeep admins, Open WebUI's check, Seerr's test call, Ollama's pull, the Healthchecks/ntfy test, qBittorrent's sign-in and changes, `project_refresh`.
- ⚠ checks, for adopting a server: a container with a kit service's name from another project (the install would stop at Start); a mount whose source moves, saying when the new folder is empty (the app starts fresh); `/tv`, `/movies` or `/downloads` coming from a folder other than `MEDIA_ROOT`'s `TV Shows`, `Movies`, `Downloads` (the /data move would point the apps at folders without the files); a media folder with files but no `Movies` or `TV Shows`; Sonarr/Radarr library folders outside `/tv`, `/movies` and `/data`; series and movies that would move to `/data` (each rescanned); torrents qBittorrent would move and recheck; Jellyfin libraries it would add (a full scan); Plex or Jellyfin running in a container while the kit runs the app; a new generated database password or encryption key where that project's app data already has data; an image the install would pin that's newer than what the container runs (the registry's manifest digest, a HEAD, against the container's RepoDigest), and RomM older than 5; RomM's Structure B library; host ports another container holds; other launchd jobs that mention Plex, Jellyfin, Glances, Docker, backups or media.
- Can't tell: an app that isn't running yet or that the kit has no key for, a registry that doesn't answer, Tailscale names already taken, whether recreated containers come up healthy. The wiring reads the apps as they run now, before any recreate.

## Secrets and preflight

- Two input modes, one result: a user-filled secrets file, or prompts at the start. Prompts append to the same secrets file (chmod 600, git-ignored).
- Random app secrets (Homarr encryption key, Gluetun control key, qBittorrent password, database passwords) go in a separate seeded file, `~/server/kit/generated-secrets.conf` (chmod 600). Each key is created once if missing and never changed. Losing this file loses database passwords and Homarr's encryption key, so backup-config and restore-config always include it, along with the answers and secrets files.
- `./kit check` (and the start of every install) checks the Mac itself: macOS 13 or newer and a supported CPU, or "this Mac can't run the kit"; memory (warns under 8 GB) and free disk (warns under 20 GB); then OrbStack installed and running with `docker compose` 2.24+. Missing software isn't a verdict on the Mac: it's listed under "To do first" with the step to take, so `check` works on a Mac that has never had the kit.
- Preflight runs before anything is installed:
  - format checks: Tailscale auth key prefix, WireGuard private key shape, Healthchecks URL shape, Homarr API key shape
  - VPN key, live: throwaway Gluetun container, confirm it connects with a non-home IP, tear it down
  - Healthchecks URL, live: one ping
  - Tailscale auth keys: format only (validating would use them up). Whether a node joined, and with a tag, is checked after the start
- Plex is native, so there is no claim token. Plex sign-in is a checklist item.

## App wiring

Config files are seeded before first start by the module's `hooks/seed` (bash, run in a subshell). If a file already exists, nothing is written and keys are read from it (an existing `config.xml`'s API key wins over the generated one):

- Sonarr, Radarr, Prowlarr `config.xml` with API keys generated into `generated-secrets.conf`, so every consumer knows the keys before anything starts. Only `ApiKey` and `LogLevel` (info) are seeded; the apps fill in the rest, and ask for a login to be created on first open (a checklist item)
- qBittorrent `qBittorrent.conf` (5.x layout: a `[WebUI]` section and `[Meta] MigrationVersion=12`): login `admin` with the generated password as qBittorrent's PBKDF2-HMAC-SHA512 hash (100,000 rounds, computed with the perl that ships with macOS, so no container), local-auth bypass (needed by Gluetun's port-forward hook) plus a whitelist of only the Docker gateway /32, `tun0`, save and temp paths. `categories.json` with `radarr` and `tv-sonarr`
- Bazarr `config/config.yaml` with its own API key and its Sonarr and Radarr connections (a partial file works; Bazarr fills in the rest). Bazarr reads any value that looks like a number as one, even quoted, and then drops it, so the *arr API keys are generated to start with a letter

Then, after the stack has started, the module's `hooks/wire` sets what lives in app databases through their APIs (`lib/api.sh`: curl and text tools, no jq). Each item is looked up by name or path first and created only if missing, so re-runs create nothing; a failed item warns, and the install goes on:

- Sonarr, Radarr and Prowlarr: a login (a login page, `admin`, the generated `ARR_PASSWORD`), made through their host settings (`PUT /api/v3/config/host`, `/api/v1/` for Prowlarr) as their own "Authentication Required" box does; the login lives in their databases, so it can't be seeded in config.xml. A login someone already made is left alone
- Sonarr and Radarr: root folders `/data/TV Shows` and `/data/Movies` (no remote path mappings; hardlinks are the apps' default, and the install warns when one has them off), and qBittorrent as download client at `gluetun:8080` (it shares Gluetun's network), login `admin` with the generated password, categories `tv-sonarr` and `radarr`. The apps log in to qBittorrent when the client is added, so this also checks the seeded password
- An install from before the `/data` layout (the kit's own before M12, or an adopted stack with `/tv`, `/movies` and `/downloads` mounts) is moved by the next `./kit install`, through the apps' APIs, with nothing moving on disk: Sonarr's series and Radarr's movies under the old root folder get `/data/...` with each app's editor (`PUT series/editor` / `movie/editor`, `moveFiles:false`, never the UI's mass edit), then Radarr's collections, both apps' import lists and their Plex/Jellyfin connections' path mappings; the old root folder is removed only once nothing is left under it. Seerr's library folders (`/tv`, `/movies`, or empty after a root folder went, which silently stops requests) become the `/data` ones. qBittorrent, signed in from this Mac: its default and incomplete paths, any category with a `/downloads` path, and each torrent still there (Set location, then a recheck). Big JSON lists go through osascript's JavaScript (`api_js`): they hold nulls, which plutil refuses.
- Prowlarr: a `flaresolverr` tag, the FlareSolverr indexer proxy (`http://flaresolverr:8191/`) carrying it, and Sonarr and Radarr as full-sync apps with the reference stack's categories (Prowlarr's own defaults leave out anime, sport and documentaries). Prowlarr checks each app's API key when it's added
- Seerr, once someone has signed in to it (its API refuses its own key before that): Sonarr and Radarr as its services, with their first quality profile and the library folders. Before sign-in the install only says so; the next run connects it. Seerr's API checks its schema's required properties (`activeProfileName`, Radarr's `minimumAvailability`, Sonarr's `enableSeasonFolders`) and answers 400 without them
- Sonarr/Radarr → Plex library updates, if Plex is enabled, signed in, and has a library of that kind (the plex module's `hooks/wire`)
- Jellyfin's setup, libraries and connections (the jellyfin module's `hooks/wire`, above). The install loads the launchd jobs before the wiring ("Health and jobs", then "Connecting the apps"), so the native apps are running by then

The old stack's scripts are a source of working details, not a template. Indexers are not added, and the installer never waits at a prompt for Seerr.

Left to the checklist: indexers (users tag Cloudflare-protected ones `flaresolverr`), quality profiles and size limits (the docs may suggest defaults), and signing in to Seerr (interactive Plex or Jellyfin sign-in), followed by `./kit install` again.

## Homarr

- A fresh Homarr gets its first account from the kit: `admin`, with the generated `HOMARR_ADMIN_PASSWORD`, and an API key for the kit, stored in `generated-secrets.conf`. It does this through the same calls Homarr's setup pages make (claim the setup, step past the welcome page, create the account, sign in, create a key), once per machine. The rest of Homarr's setup (server settings, first board) is left to the user, who signs in as admin to finish it. Homarr 2 takes its address from each request, so it needs no `BASE_URL`.
- A Homarr that already has an account (set up by hand, or adopted) needs a key from its owner: `HOMARR_API_KEY` in `secrets.conf`, which wins over the kit's own. The install says so and goes on without tiles until then.
- The installer then creates a tile (app) for each app via Homarr's published API, opening the app's Tailscale address (this Mac's when the node isn't up), and its widget connection (integration) linked to the tile. Integrations go through Homarr's internal API, as Homarr's own pages do (its published API can't create them). Each is looked up by name first, so re-runs create nothing; tiles aren't changed once made. Plex token is read from native Plex preferences. Jellyfin's key is the one the kit makes (or the owner's).
- Integrations are a separate step behind `HOMARR_INTEGRATIONS` (default on), so falling back to tiles only is a default flip.
- Homarr's internal API is unversioned, so failures warn and continue. Homarr publishes only exact version tags (`v2.3.0`) and `latest`, no major-version tag; keeping updates within one major version is update-all's job (it can compare release tags).
- No boards are created. Custom widgets ship with their module as `homarr-widget.json` (a `homarr-custom-widget-v2` definition without its template) and `homarr-widget.jsx` (the template); the install imports each once, by name, through tRPC `customWidget.import` (checked against Homarr 2.11). Modules: health (Server health); glances (Mac Host Info, whose network charts follow the `en*` interface with the most traffic, from Glances' own list, rather than always `en0`). Templates are Homarr's restricted JSX: one-expression callbacks with plain parameter names, no `const`, no `Object.keys`. The install records each widget it imports or updates in `~/server/kit/homarr-widgets.lock` (seeded state): `name|fingerprint|updatedAt`, a hash of the two files and Homarr's updatedAt just after. When a module's definition changes, `./kit install` (not update-all) offers to update the widget through `customWidget.update`, run in Terminal; otherwise it only notes it. If Homarr's updatedAt no longer matches the recorded one, the widget was changed in Homarr since (enabling or disabling it counts); the install says so and replaces it only if you agree (default no). Saying no records the new fingerprint with the old time, so the same definition isn't offered again and the next one is again treated as changed in Homarr. A widget imported before the lock existed is adopted silently when its template matches the module's.

## Updates and image pins

- Image pins (tag@digest) live in a lock file on each machine, untracked: `~/server/<project>/images.lock`, one `service repo:tag@sha256:... [track]` line per service. track is there only when the service follows a release series. Compose files in the repo carry only `repo:tag`. A generated `zz-images.yml` override applies the pins through Compose's own file merge. Update scripts refresh the lock and regenerate the override. No repo pull needed to update images. Install pins only services that have no pin yet, pulling the tracked tag (the compose file's, or a hold's); it never moves an existing pin, and re-pins only when a service's image repo changes. Deleting a line from `images.lock` makes the next install pin it afresh. A disabled module's pins stay in the lock but leave `zz-images.yml`.
- Backup, update and restore are generic per-project runtime scripts. What they need per project comes from the generated `runtime.conf`, built from each module's `module.conf`: `BACKUP_EXCLUDE` (app data paths left out, such as MediaCover and logs), `BACKUP_EXPECT` (files a good backup must hold, such as each app's database) and `AFTER_START` (a check run after a start, such as check-media-stack). Small module hooks only where needed (online SQLite copies, .dmg version checks). `backup-<module>` and friends are thin wrappers.
- `update-project <p>` opens a maintenance window, backs the project up first, then pulls each service's tracked tag (the lock's track, else its tag) and re-pins it to the new digest. When no pin moved it restarts nothing. Otherwise it rewrites `zz-images.yml`, starts the project (`up -d --wait`), runs the project's check and prints the restore command that undoes the update. `update-all` prunes unused images and build cache once at its start, updates the projects in order, stops at the first failure, closes the window and runs check-health. It is manual by default; `UPDATE_SCHEDULE=weekly` (an answer) adds a weekly launchd job, Sunday 06:30, an hour after the backup.
- Version holds: a module's `holds` file lists known-good holds, `service tag yyyy-mm reason`. The answers file can add or lift holds per machine (`HOLD_<service>=<tag>  # <reason>, yyyy-mm`; an empty value lifts one). `./kit status` lists holds with their age so stale ones stand out. With the wud module, WUD's `wud.tag.include` label follows the hold (see the wud module).
- Registries list tags in pages (ghcr.io at most 1,000 per page; Open WebUI has tens of thousands of build tags): the lookup follows the `Link` header to the last page, and fails rather than choose from a partial list.
- A hold's tag can be a release series, such as `v2.*`: the pin is then the newest release tag matching it, numbers compared one by one; pre-releases and suffixed tags (`v3.0.0-beta.1`, `v2.11.1-alpine`) never match. The install and update-project both resolve it from the registry's tag list (Docker Hub, and ghcr.io for ghcr and lscr images, with anonymous tokens). The media stack holds Homarr at `v2.*`: the kit's account setup, tiles and widgets use Homarr's internal API, and Homarr publishes no major-version tag (its image's version label just says `main`).

## Backups

- One weekly launchd job (Sunday 05:30) runs `backup-all`: inside a maintenance window it backs up each project in order, then config, then runs copy-backups, and reports every failure at the end. Native modules with a `backup-<module>` script (`NATIVE_MODULES` in `runtime.conf`, in backup order) run after the projects: `backup-plex`, `backup-jellyfin`.
- `backup-project <p>` writes `project.tgz` (`.env`, `images.lock`, `compose.override.yml`) and `appdata.tgz`, less `BACKUP_EXCLUDE`. For a consistent copy it stops the project's running services that mount app data and starts them again afterwards, on failure too. A service that doesn't come back is recreated (`up -d --no-deps --force-recreate`): Docker can refuse to start a container it still holds an old process record for ("failed to create task: AlreadyExists", seen on a real server after OrbStack trouble), and both `start` and a plain `up -d` reuse that container. App data lives in `~/server/appdata`, so a new container loses nothing. If one still isn't running, the backup is kept but `backup-project` fails, naming only those services. restore-project and update-project do the same when their `up -d --wait` leaves a service not running (`wait_healthy`). It writes `manifest.txt` (pins and sizes) and fails when a `BACKUP_EXPECT` file is missing. Backup folders are private (700).
- `restore-project <p> [backup]` takes the newest backup by default, shows how its pins differ from the current ones, and asks you to type `restore` (or `RESTORE_YES=1`). It sets the current state aside first in `pre-restore-<date>` (never pruned or copied), restores the pins and `compose.override.yml`, swaps the app data, keeps the current MediaCover (it isn't backed up), then starts the project and runs its check. `.env` isn't restored: the install regenerates it.
- `backup-config` keeps the answers, secrets and generated secrets, `ntfy-tested`, `homarr-widgets.lock`, every `images.lock` and `compose.override.yml`, and `local-modules`, with a copy of restore-config next to them. `restore-config` runs from that folder on a fresh Mac too; it keeps the files it replaces in `replaced.tgz`.
- `backup-plex` copies Plex while it runs: its databases with SQLite's online backup (`sqlite3` is part of macOS), the rest of "Plug-in Support" without caches or Plex's own dated database copies, and its preferences (`defaults export`: the server's identity and sign-in). Posters and artwork are left out; Plex rebuilds them. A Plex that hasn't been set up has nothing to back up, which isn't a failure. `restore-plex [backup]` asks first, quits Plex normally (it ignores SIGTERM; a normal quit doesn't make its job restart it), sets the current data aside in `pre-restore-<date>`, restores both and starts the job again.
- `backup-jellyfin` copies Jellyfin while it runs: its config, data, plugins and root folders, the SQLite databases (users, watch history, libraries, API keys) with the online backup; artwork, cache, logs, transcodes and keyframes are left out. `restore-jellyfin [backup]` asks first, stops its job (a clean shutdown), sets the current folders aside in `pre-restore-<date>`, restores them (carrying transcodes and keyframes over) and starts the job again. Restore into the same or a newer Jellyfin: an older one can't open a migrated database.
- Keep 8 locally (`KEEP` in `runtime.conf`).
- `copy-backups` to an external drive: `BACKUP_DRIVE` (an answer) is off when empty; a drive itself (`/Volumes/<name>`) gets a folder named after the Mac (`<computer-name>-backups`). APFS recommended. It only copies when the drive is mounted under `/Volumes`, and prunes per project on the drive only, keeping 26 (half a year of weeks). Each run records how it went in `~/server/logs/copy-backups.status` (when it tried, ok / skipped / failed / off, why, when it last copied): `./kit status` shows it, and check-health warns (a setting, not an outage) when `BACKUP_DRIVE` is set and nothing has been copied for over 15 days.

## Mac settings

- The installer asks laptop or server.
- Server: the power settings `sleep 0`, `disksleep 0`, `autorestart 1`, `womp 1` and `powernap 0` (`lib/mac.sh`), filtered by `pmset -g cap` so unsupported settings are skipped, and only the ones that differ. The install shows them and applies them with `sudo pmset -a` once you agree in Terminal (an admin's password); run from a script, or if sudo fails, it prints the command for an admin.
- Laptop: skip power settings.
- Native apps start at login from the kit's own launchd jobs (above), not login items.
- Auto-login is a checklist item (blocked by FileVault, would require handling the password).
- The Mac's own Tailscale app is not installed by the kit. In server mode the checklist recommends it for remote SSH and Screen Sharing. check-health watches it according to `HOST_TAILSCALE=auto|on|off` in the answers file (default `auto`: only if it's installed).

Prerequisite. Installed with brew if present. Otherwise preflight stops with the download link and waits. Its first launch needs the user at the screen anyway.

## Existing machines

The two machines already running an older setup are adopted once, by hand, after the kit works on a test machine. Nothing for adoption ships in the repo beyond `./kit install --plan`, run (and its ⚠ lines settled) before the first install there.

## Testing and order of work

1. Repo skeleton and base install, tested in a separate standard user account on the M4 MacBook Air, with `APPS_DIR=~/Applications`. Not a macOS VM: Apple Silicon allows nested virtualization only for Linux guests, so OrbStack can't run inside a macOS VM. Everything the kit writes is under that user's home folder, so deleting the user (with its home folder) removes it all. OrbStack in `/Applications` is shared with the owner's account; quit it in the owner's account during test runs.
2. Modules one at a time.
3. Test the Intel and no-Homebrew paths (.dmg and uv fallbacks) on a spare Intel Mac. The M4 test account can't cover them.
4. Adopt the owner's server, then his brother's.
