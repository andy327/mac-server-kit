# Proposal: repo skeleton and base install

For review. Nothing here is implemented. Once it's agreed, the settled parts move into `docs/design.md` and this file is deleted.

## 1. Repo layout

```
kit                         entry point: install | check | add | disable | status
lib/                        sourced by ./kit only, never installed
  common.sh                 log/warn/die, prompts, confirm, kv-file reader/writer
  config.sh                 answers, secrets, generated secrets, holds
  modules.sh                discovery, validation, dependency order, enabled list
  preflight.sh              format checks, live checks (throwaway Gluetun, HC ping)
  render.sh                 ${VAR} template rendering (awk), .env, serve.json, plists
  compose.sh                project assembly, COMPOSE_FILE, up/down, wait-healthy
  native.sh                 brew / .dmg (hdiutil) / uv installers, login items
  macos.sh                  pmset (filtered by pmset -g cap), laptop vs server
  arr.sh                    *arr/qBittorrent API wiring (create-if-missing)
  homarr.sh                 Homarr apps, then integrations (warn and continue)
runtime/                    copied to ~/server/bin on every install (generated)
  update-all  backup-all  copy-backups
  check-health  show-health-history  export-health-status
  start-maintenance  end-maintenance
  lib/runtime.sh            shared by runtime scripts: enabled list, docker context,
                            maintenance window helpers, keep-N pruning, lock → images.yml
  backup-project            generic, driven by ~/server/kit/modules/<name>/; backup-<module>
  update-project            and restore-<module> are thin generated wrappers around these
  restore-project
modules/
  core/                     base: server-wide answers (role, time zone, media root, media server,
                            backup drive, update schedule); later the Mac settings, backup-all,
                            update-all and maintenance windows
  media-stack/              base: gluetun, qbittorrent, prowlarr, sonarr, radarr, bazarr,
                            flaresolverr, seerr, homarr, glances-proxy,
                            stack + dashboard Tailscale nodes
  health/                   base: health-web, log-health job
  glances/                  base: native Glances + its launchd job
  plex/                     native; enabled by the media-server question
  jellyfin/  tracearr/  wud/  romm/  ollama/  open-webui/  karakeep/
templates/
  launchd.plist.tmpl        one template for every job (label, args, schedule, logs)
  env-header.tmpl           "generated by ./kit, do not edit" banner
docs/
  design.md  checklist.md (manual steps, assembled per machine at the end of install)
tests/
  run                       dev-machine test runner (/bin/bash 3.2, no dependencies)
  lib.sh  test-*.sh
README.md  .gitignore  .shellcheckrc
```

Base components are modules too, with `KIND=base`. They're always enabled and `./kit disable` refuses them. Treating them as modules means backup-all, update-all and check-health have one code path. Plex and Jellyfin are ordinary modules. The media-server question just enables one or both, and preflight requires at least one.

## 2. Module folder format

```
modules/<name>/
  module.conf               required, key=value (format below)
  prompts                   answers/secrets this module asks for, with defaults
  env.tmpl                  lines rendered into the project's generated .env
  compose.yml               services; own project, or a fragment of another project
  compose.<project>.yml     optional fragment merged into another project
                            (e.g. romm ships compose.media-stack.yml putting homarr on romm's network)
  serve/<node>.json.tmpl    optional: Tailscale serve config for a node this module owns
  hooks/                    install-time steps, sourced by ./kit in a subshell, each optional:
    native                    install/upgrade native prerequisites (brew / no-brew paths)
    seed                      create-if-missing app config before first start
    wire                      create-if-missing settings through app APIs after start
    homarr-apps
    homarr-integrations
  hooks/backup, hooks/restore, hooks/update
                            optional runtime extras only where the generic scripts can't
                            cover it (Plex/Jellyfin online SQLite copies, .dmg version checks,
                            Open WebUI's release-tag lookup)
  holds                     known-good version holds shipped with the module
  help                      KEY|about|where to get it|after|when: shown at the prompt, by
                            ./kit prepare and in the templates (a test requires one per asked key)
  ready                     group|when|text: what to have ready that isn't a key
                            (groups: before, machine, after)
  checklist.md              manual steps, appended to the printed checklist
  widgets                   Homarr widgets/integrations this enables (post-install list)
```

`module.conf`:

```
DESCRIPTION="RomM game library"
KIND=optional                    # base | optional
PROJECT=romm                     # compose project; "media-stack" = fragment of the stack
REQUIRES="ollama"                # all must be enabled
REQUIRES_ONE_OF="plex jellyfin"  # at least one (tracearr)
TS_NODES="romm"                  # Tailscale node ids this module owns
EXPOSE_DEFAULT=tailnet           # funnel | tailnet, asked once per node
BACKUP_ORDER=30                  # backup-all and update-all run modules in this order
NATIVE_HEALTH="Jellyfin|8096|/health|fail"   # read by check-health at runtime
```

`prompts`, one per line, `|`-separated. No eval, no associative arrays:

```
# file|key|default|validator|question
answers|GAMES_ROOT|$HOME/Games|dir|Where should ROMs and BIOS files live?
secrets|IGDB_CLIENT_ID||optional|IGDB client ID (Enter to skip)
gen|ROMM_AUTH_SECRET_KEY|hex32||
```

`gen` keys are random secrets the kit creates once (see section 3). `holds` format: `<service> <tag> <yyyy-mm> <reason...>`, for example `tracearr-db pg18 2026-11 major version needs a data migration`.

`module.conf` is read with a `conf_get <file> <key>` reader (sed), never sourced, so modules can't leak variables into each other. Hooks are code and are sourced, but each runs in a subshell that receives only the answers, secrets and helpers.

## 3. Machine files (all under `~/server/`, never inside the checkout)

Keeping every machine file outside the repo checkout means a bad `.gitignore` can't leak one.

| File | Kind | Contents |
|---|---|---|
| `~/server/answers.conf` | user-owned | choices: paths, media server, VPN provider, node names, exposure, laptop/server, schedules, `MODULES=`, holds |
| `~/server/secrets.conf` (600) | user-owned | keys the user supplies: WireGuard key, Tailscale auth key, Healthchecks URL, ntfy topic, Homarr API key, metadata credentials |
| `~/server/kit/generated-secrets.conf` (600) | seeded | random app secrets: Homarr encryption key, Gluetun control key, qBittorrent password, Tracearr DB password, etc. Created per key if missing, never changed. Always in backup-config/restore-config, with answers.conf and secrets.conf |
| `~/server/kit/enabled` | generated | resolved enabled modules in dependency order (read by runtime scripts) |
| `~/server/kit/runtime.conf` | generated | what runtime scripts need: NAME, HC URL, ntfy topic, backup drive, keep counts, native-app health lines |
| `~/server/<project>/.env`, `compose.d/`, `tailscale/*.json` | generated | see section 4 |
| `~/server/<project>/images.lock` | seeded, then maintained by update scripts | image pins |
| `~/server/<project>/compose.override.yml` | user-owned | Compose overrides |
| `~/server/local-modules/<name>/` | user-owned | same format as `modules/` |

Format for all `.conf` files: `KEY=value` one per line, `#` comments, optional double quotes stripped, no shell expansion. The kit parses them and never sources them, so a `$` in a password is safe. Keys match `[A-Za-z0-9_.-]+`, which allows `HOLD_tracearr-db=pg18 # reason, 2026-11`.

`answers.conf` example (placeholders only):

```
MACHINE_ROLE=server              # server | laptop
MEDIA_ROOT=/Users/<you>/Media
MEDIA_SERVER=plex                # plex | jellyfin | both
VPN_PROVIDER=protonvpn           # protonvpn | nordvpn
TIMEZONE=America/New_York
MODULES=wud romm
TS_NODE_media=media
TS_NODE_dashboard=dashboard
EXPOSE_media=funnel
BACKUP_DRIVE=
UPDATE_SCHEDULE=off              # off | weekly
HOMARR_INTEGRATIONS=on
HOST_TAILSCALE=auto              # auto | on | off: check-health watches the Mac's Tailscale app
HOLD_meilisearch=v1.41 # <reason>, 2026-11
```

`./kit install --secrets <file>` reads that file as the secrets file for the run and copies it to `~/server/secrets.conf` (600) if it lives anywhere else.

## 4. How `./kit` discovers and assembles modules

1. **Discover:** `modules/*/module.conf`, then `~/server/local-modules/*/module.conf`. A local module with the same name as a repo module is an error, not an override.
2. **Enable set:** base modules, plus `plex`/`jellyfin` from `MEDIA_SERVER`, plus `MODULES=`. `./kit add x` appends `x` to `MODULES=` and re-runs install. `./kit disable x` removes it, runs `compose down` (no `-v`) for its services, unloads its jobs and re-runs the generate step.
3. **Resolve:** check `REQUIRES` and `REQUIRES_ONE_OF`, then topologically sort with repeated passes over a space-separated list (bash 3.2 friendly). The result goes to `~/server/kit/enabled`.
4. **Assemble each project** (no YAML parsing):
   - Copy the owning module's `compose.yml` and every enabled module's `compose.<project>.yml` into `~/server/<project>/compose.d/`.
   - Write `COMPOSE_FILE=compose.d/a.yml:compose.d/b.yml[:compose.override.yml]` into the project's generated `.env`. Compose reads `.env` on a plain `docker compose up`, so manual commands behave the same. Setting `COMPOSE_FILE` turns off auto-loading of `compose.override.yml`, so the kit appends it when it exists.
   - This replaces the reference's profiles. A disabled module's services simply aren't in the file list.
5. **Images:** compose files in the repo carry `image: repo:tag` only and are never rewritten. A generated `compose.d/zz-images.yml` holds one `image: repo:tag@sha256:…` per enabled service, taken from `images.lock`, and goes last in `COMPOSE_FILE` before the user's override. Compose's own merge makes the pin win. That means no awk over YAML, and the lock is the only per-machine image state. On install, services missing from the lock are pulled and pinned, and existing pins are never moved (seeded). `update-project` refreshes the lock (tracked tag or hold), regenerates `zz-images.yml` and runs `up -d --wait`. Holds (module `holds` plus `HOLD_*` answers) choose the tracked tag and the WUD hide label.
6. **Tailscale:** each node's `serve.json` is rendered from module serve templates. The media node collects one handler per port contributed by enabled modules. Funnel is set by `EXPOSE_<node>`. One reusable, pre-approved auth key (`TS_AUTHKEY`) is used for every node's first login, with an optional per-node `TS_AUTHKEY_<node>`.

## 5. Base install plan (`./kit install`)

Every step is skip-if-done.

| # | Step | Notes |
|---|---|---|
| 1 | Host preflight | macOS version, arch, brew present?, disk space, OrbStack installed (brew if present, else stop with the download link) and running, `docker compose` version (needs `COMPOSE_FILE` and `service_healthy`) |
| 2 | Answers | ask only for keys missing from `answers.conf`, then append them |
| 3 | Secrets | `--secrets` file or prompts for missing keys; format checks; generate missing `gen` keys |
| 4 | Live checks | throwaway Gluetun (non-home IP, for ProtonVPN also a forwarded port), one Healthchecks ping, ntfy test message (optional) |
| 5 | Mac settings | server: pmset with sudo after confirmation, filtered by `pmset -g cap`. Laptop: skip |
| 6 | Layout | `~/server/{bin,appdata,backups,logs,kit}`, MEDIA_ROOT subfolders |
| 7 | Native | uv (no brew) → Glances bound to 127.0.0.1 with 10s refresh. Plex via cask or .dmg, then a login item |
| 8 | Generate | `.env`, `compose.d/`, `COMPOSE_FILE`, serve.json, health-web nginx.conf, plists, `runtime.conf`, `enabled`; lock pins for new services; runtime scripts into `~/server/bin` |
| 9 | Seed | before first start, create if missing. Sonarr/Radarr/Prowlarr `config.xml` with API keys from `generated-secrets.conf`, so every key is known before anything starts. qBittorrent `qBittorrent.conf` with paths, `tun0`, local-auth bypass, Docker gateway /32 whitelist and the generated password as a PBKDF2 hash (computed with openssl 3 in a throwaway alpine container), plus `categories.json`. Bazarr `config.yaml` with its Sonarr/Radarr connections. If a config already exists, nothing is written and keys are read from it |
| 10 | Start | `docker compose up -d --wait --wait-timeout 300` per project in dependency order |
| 11 | Wire | only what lives in app databases, all create-if-missing (look up by name first). Sonarr/Radarr: root folders, qBittorrent client (`gluetun:8080`), Plex library updates if the Plex token is readable. Prowlarr: `flaresolverr` tag + FlareSolverr proxy, Sonarr/Radarr apps, sync. No indexers, no Seerr prompt |
| 12 | Jobs | load `log-health` (5 min), `backup-all` (weekly), `glances`, optional `update-all`; all `io.github.andy327.mac-server-kit.<job>`, using bootout/bootstrap so re-runs pick up changes |
| 13 | Homarr | with `HOMARR_API_KEY`: apps, then integrations (warn and continue). Without it: print how to create it and say to re-run |
| 14 | Report | URLs, health iframe URL, available widgets, assembled checklist |

Runtime parity with the reference: maintenance windows (`.maintenance` file with start, expiry and reason), check-health with `--log` and Healthchecks pings plus ntfy alerts on state change, keep-8 pruning, copy-backups' mount checks. backup-all replaces per-project jobs. It runs `backup-<module>` for each module in `enabled`, then config, Plex and Jellyfin. check-health finds projects and native apps from `enabled` and `runtime.conf` instead of scanning `~/server`.

## 6. Implementation milestones (each tested in the VM from a snapshot)

1. `kit` + `lib/common|config|modules`: discovery, enable/resolve, answers/secrets I/O, `./kit check`, `./kit status`.
2. media-stack generate + start (no Tailscale): lock, apply-lock, COMPOSE_FILE, seed, wait-healthy.
3. Wiring.
4. Tailscale nodes + serve.json + Homarr.

6. backup-all / restore / update-all / copy-backups.

## 7. Findings from the two checks

**Glances on 127.0.0.1: works.** Tested on this Mac under OrbStack, a listener bound only to `127.0.0.1` on the Mac was reachable from a container at `host.docker.internal` (resolves to `0.250.250.254`). It was also reachable through an `alpine/socat` relay identical to glances-proxy. So Glances runs with `--bind 127.0.0.1`, glances-proxy is unchanged, and Glances is off the LAN. The test used a plain TCP listener, not Glances itself. The VM run will confirm with the real thing.

**Ollama without Homebrew:** install `Ollama.app` from the official .dmg (same hdiutil helper as Jellyfin). The kit's own job `io.github.andy327.mac-server-kit.ollama` then runs `/Applications/Ollama.app/Contents/Resources/ollama serve` with `OLLAMA_HOST=127.0.0.1:11434` and the flash-attention/KV-cache env vars, with KeepAlive and logs under `~/server/logs`. With brew, use the formula's binary in the same plist, not `brew services`. Three catches:
- The app registers a login item and starts its own server, which would fight the job for port 11434. The kit removes that login item and never opens the app.
- The app's auto-update only runs inside the app, so `update-ollama` checks the latest release version and swaps the .dmg itself.
- Ollama needs macOS 14+, and Intel Macs are CPU-only. Preflight warns on both.

Running the bundle's CLI headless isn't officially documented, so the VM run has to confirm it.

## 8. Decisions (now in design.md)

1. **User-owned files:** append-only. The kit only appends missing keys and edits the `MODULES=` line. Random app secrets go in `generated-secrets.conf`, and backup-config/restore-config always include it with the answers and secrets files. CLAUDE.md now says "never overwritten or regenerated."
2. **Bazarr and FlareSolverr:** both in base. Prowlarr gets the FlareSolverr proxy with its `flaresolverr` tag. Bazarr's connections to Sonarr and Radarr are seeded in its config.yaml, which works because the *arr API keys are generated up front. Seeding a partial config.yaml is new, so the VM run must confirm it. Bazarr's settings API is the fallback.

## 9. Where this departs from the reference scripts

The reference was used for working details only. These replacements produce the same install:

| Reference | Kit | Why |
|---|---|---|
| read *arr API keys from config.xml after first start | generate them and seed `config.xml` | every consumer (Prowlarr, Bazarr, Homarr, health) knows its keys before start; no ordering or waiting |
| qBittorrent: scrape the temporary password from `docker logs`, then set prefs via API | seed `qBittorrent.conf` + `categories.json` | the log format has already changed once (configure.sh carries two fallbacks); a seeded file is deterministic |
| refresh-image-lock rewrites `image:` lines in docker-compose.yml with awk | generated `zz-images.yml` override from `images.lock` | repo compose files stay untouched; Compose does the merge |
| profiles in one big compose file | `COMPOSE_FILE` list of enabled module files | disabled modules aren't in the config at all |
| hand-rolled wait loop | `up -d --wait` | built into Compose |
| one hand-written backup/update/restore script per project | generic `*-project` scripts + module metadata + small hooks | one code path; a new module needs no new scripts |
| backup-media-stack finds the stack from container labels | paths come from the kit's own records | the kit already knows them |
| check-health scans `~/server` and a hard-coded app list | reads `enabled` and module health declarations | follows add/disable automatically |
3. **NordVPN:** plain Gluetun WireGuard/NordLynx with no port forwarding. The one-off DNS and HTTPPROXY settings are left out.
4. **Host Tailscale app:** not installed. `HOST_TAILSCALE=auto|on|off` (default auto) controls the check-health check, and a server-mode checklist item recommends the app for SSH and Screen Sharing.
